# Архитектура

## Главный принцип
Не строить набор микросервисов заранее.

Для текущей задачи рациональнее использовать модульную архитектуру с четкими границами. Это дешевле и проще в поддержке, но позволяет позже вынести отдельные части в сервисы.

## Предлагаемый стек

### Frontend
- Next.js
- TypeScript
- SSR/SSG
- компонентная библиотека
- API-доступ к CMS

### CMS
- Directus
- PostgreSQL

CMS отвечает за:
- страницы;
- блоки;
- изображения;
- SEO-поля;
- draft/publish;
- роли редакторов;
- preview.

### Заявки
Отдельный модуль Leads:
- прием формы;
- валидация;
- сохранение;
- Telegram;
- email;
- WhatsApp;
- логирование;
- retry;
- anti-spam.

### Инфраструктура
- Docker
- reverse proxy
- HTTPS
- PostgreSQL
- backup
- staging
- production
- CI/CD

## Логическая схема

```text
Пользователь
   |
   v
Next.js
   |
   |------> Directus CMS ------> PostgreSQL
   |
   |------> Leads API ---------> PostgreSQL
                         |------> Telegram
                         |------> Email
                         |------> WhatsApp
```

## Библиотека страниц
Страница должна собираться из контролируемых блоков:

- Hero
- Text
- Image + Text
- Cards
- Benefits
- CTA
- FAQ
- Logos / Partners
- Form
- Contact
- Custom section

Редактор может менять содержимое и порядок блоков, но не должен иметь свободный доступ к HTML/JS.

## Когда реально нужны микросервисы
Выносить модуль в отдельный сервис стоит только если появляется конкретная причина:
- высокая нагрузка;
- отдельная команда;
- независимое масштабирование;
- несколько сайтов используют один backend;
- тяжелые интеграции;
- отдельные требования по надежности.

До этого — модульный монолит и отдельные контейнеры.
